### 2026-07-14 — Svelte `{#key}` blocks cause DOM flicker on frequent updates

- **Problem**: Sticky headings flickered visibly during scroll. The Svelte template used `{#key array}` blocks around the heading list. Svelte's `{#key}` DESTROYS and RECREATES all child DOM nodes whenever the key expression changes. Since `setHeadingsInView()` passed a new array on every scroll tick (throttled 50ms), the entire heading bar was torn down and rebuilt 20 times per second.
- **Solution**: Replaced `{#key}` blocks with keyed `{#each ... (heading.index)}`. This lets Svelte diff incrementally — it only adds/removes individual heading DOM nodes that actually changed, instead of destroying everything.
- **Files**: `src/ui/StickyHeader.svelte`
- **Key insight**: `{#key}` in Svelte is a sledgehammer — use it only when you genuinely need to reset component state. For list rendering, keyed `{#each}` is almost always the right choice.

### 2026-07-14 — Reference equality defeats optimization guards

- **Problem**: Added a content-equality check in `stickyHeader.ts` to skip `$set()` when headings hadn't changed. But the check compared `getExpectedHeadings === lastGetExpectedHeadings` by reference. The problem: `makeExpectedHeadings()` created a NEW closure on every `setHeadingsInView()` call, so the reference was always different. The optimization never fired.
- **Solution**: Cached the `getExpectedHeadings` closure on `FileResolveEntry` (created once during init/layout-change, reused across scroll events). Now the same reference is passed every time, and the equality check works.
- **Files**: `src/plugin.ts`, `src/stickyHeader.ts`, `src/types.d.ts`
- **Key insight**: When optimizing with reference equality checks, make sure the references are actually stable. A factory function called inline will always produce new references.

### 2026-07-14 — Don't cache too aggressively — know what triggers what

- **Problem**: First attempt at fixing flicker removed `retrieveHeadings()` from `setHeadingsInView()`. But it also accidentally removed heading refresh on layout-change and metadata-resolve, because those code paths routed through `setHeadingsInView` via `handleComponentUpdate` and `handleResolve`.
- **Solution**: Kept `setHeadingsInView` using cached headings (fast scroll path), but restored `retrieveHeadings()` calls in `handleComponentUpdate` (layout changes: edit/preview switch, pane resize) and `handleResolve` (content changes: headings added/removed). The invariant: scroll = fast (cached), layout-change/content-change = recompute.
- **Files**: `src/plugin.ts`
- **Key insight**: Before removing an expensive call, trace ALL callers and understand which events trigger them. "Expensive on scroll" doesn't mean "remove everywhere" — it means "remove from the scroll path only".

### 2026-07-14 — CodeMirror 6 virtualizes content — offsets shift during scroll

- **Problem**: After caching headings to prevent flicker, the sticky header stopped updating during scroll. It showed ALL headings stacked in rows instead of just the current one. Root cause: heading offsets (pixel positions) computed at initialization were stale by the time the user scrolled.
- **Why**: CodeMirror 6 virtualizes off-screen content. `cm.lineBlockAt()` returns different positions as you scroll because content is lazily rendered. Preview mode has similar behavior with section heights. Offsets computed once at init are wrong during scroll.
- **Solution**: Recompute **offsets** on every scroll tick (synchronous — `getHeadings()` from metadata cache + `getShownHeadings()` via `cm.lineBlockAt` or section iteration), but reuse **cached titles** (the expensive async `parseMarkdown()` part) via a `Map<string, string>` for O(1) lookup. This keeps scroll fast (no async, no DOM element creation) while having correct offsets.
- **Files**: `src/plugin.ts` (`setHeadingsInView`)
- **Key insight**: In CodeMirror 6, you cannot cache line positions across scroll events. The positions are only valid for the current viewport state. Cache the expensive parts (rendered markdown titles), not the volatile parts (pixel offsets).

### 2026-10-15 — Degenerate-rect fallback clobbers good anchor tops; positioning context must match the measured element by construction

- **Problem**: The sticky header pinned to the wrong position (or jumped) in three situations: (1) hidden/detached leaves — `computeEffectiveTop` returned a fallback `max(0, userNudge)` when rects were degenerate (height 0), and any recompute triggered while the leaf was hidden (global `layout-change`, settings change, resize, settle timers) wrote that fallback over the correct top; (2) theme/other-plugin overrides or class refcount races removed the `.sticky-headings-mount` / `.has-sticky-headings` positioning classes, so the CSS containing block (`top:` ancestor) no longer matched the measured `main.parentElement` and the header resolved its `top:` against a different ancestor; (3) `detachLayoutListeners()` set `observedContainer = null`, clobbering the fresh assignment in the parent-change reactive block and causing ResizeObserver disconnect/reconnect churn on every `main` re-bind (which happens whenever the headings `{#if}` block flips).
- **Solution**: (1) `computeTopFromRects` (pure, bun-tested) returns `null` for zero-height rects as a skip signal, and `recomputeTop` only writes when the result is non-null — never write a position derived from degenerate rects, keep the last good value. (2) Set `parentElement.style.position = 'relative'` inline in the parent-change block — identity by construction beats any class lifecycle. (3) `detachLayoutListeners` no longer resets `observedContainer`; the reactive block orders detach → attach → inline style → assign `observedContainer` → settle. Plus: `handleComponentUpdate` calls `refreshAnchor()` early (before the async `retrieveHeadings`) and `active-leaf-change` refreshes known items directly, so fast mode toggles / tab switches correct within a frame. Debug: `document.body.dataset.stickyHeadingsDebug = '1'` enables `logAnchor` traces (trigger, prev/next top, anchor vs parent rects, `offsetParent` agreement).
- **Files**: `src/utils/viewportAnchor.ts`, `src/utils/anchorDebug.ts`, `src/ui/StickyHeader.svelte`, `src/plugin.ts`, `src/utils/viewportAnchor.test.ts`
- **Key insight**: Never write a computed position derived from degenerate rects; make the CSS containing block match the measured element by construction (inline style on the exact measured node), not by class lifecycle. `null` is a better API than a fallback number — it forces the caller to decide what "skip" means.
### 2026-10-16 — Delta-dependent top formulas clamp-saturate and kill user input

- **Problem**: The "Desktop header position" slider appeared dead, and the sticky header jumped between two visual anchors ("pinned to different things") across tabs/modes. `computeEffectiveTop` computed `effectiveTop = max(0, round(contentElRect.top − containerRect.top + userNudge))` — i.e. `max(0, nudge − delta)` where `delta = containerRect.top − anchorRect.top`. In the ZettelPublish vault the note-toolbar + theme push the editor container down by ≥31px (the user's slider value), so every nudge clamped to 0. The same delta-dependence meant the header's visual anchor changed whenever deltas changed at runtime (tab switches, edit/preview toggles measure against different geometry). The Oct 2 contentEl anchoring (d7fe625) was built on an unresolved analysis.
- **Solution**: Anchor `top` relative to the CSS containing block the header actually renders against (`main.parentElement`, already `position: relative` inline), offset purely by the user slider: `effectiveTop = max(0, round(userNudge))`. Rects are now used ONLY as the visibility/degeneracy guard (zero height → `null` skip, preserving the hidden-leaf clobber fix). Pure core refactored to `computeTopFromRects(anchorHeight, containerHeight, userNudge)` — there is no delta to clamp. Slider descriptions updated to match the mental model: header anchored to the top of the visible content area, slider adds offset below it.
- **Files**: `src/utils/viewportAnchor.ts`, `src/utils/viewportAnchor.test.ts`, `i18n/en/index.ts`, `i18n/zh/index.ts`
- **Key insight**: Measure against the element CSS resolves against, and make user offsets independent of measured geometry — a formula that mixes user input with measured state can saturate and kill the input.

### 2026-10-17 — Headers missing in already-open notes after re-enable/reload — event-driven init needs a catch-up pass

- **Problem**: Toggling the plugin off/on (or app reload, or hot-reload deploys) left ALL already-open markdown notes without a sticky header — or with stale DOM from the previous instance. 5th-round root evidence from a live debug trace: plugin loaded at 01:43:56Z, `trace-open` logged, then ZERO anchor/mount lines despite the user staying focused on a note with headings and dragging settings. `onload` only created `StickyHeaderComponent`s inside event handlers (`active-leaf-change` / `file-open`) — those events never fire for leaves that predate the plugin's load.
- **Solution**: Added an `onLayoutReady` catch-up pass in `onload` that iterates all leaves and calls the existing per-leaf init (`initStickyHeaderComponent`) for each already-open `MarkdownView`. Strictly idempotent (skips leaves already in `fileResolveMap`, skips `mode === 'disable'`, skips leaves whose `getFile()` is still null — the event handlers cover those later), per-leaf try/catch so one broken leaf can't kill the rest, and silent (debug-gated logging only). No retries scheduled from this passive pass.
- **Files**: `src/plugin.ts`
- **Key insight**: Event-driven init needs a catch-up pass for state that predates the plugin's load — a toggle on/off always needs catch-up, or the user tests a ghost.
- **Addendum (2026-10-17)**: The catch-up pass introduced a new race — layout-ready catch-up, the 100ms `checkFileResolveMap` timer, and the 5s health check can all call `initStickyHeaderComponent` for the same leaf id while `retrieveHeadings` is in flight, both pass the `fileResolveMap.has(id)` re-check, and the second map-set orphans the first component (DOM + EventRef leaked). Fixed with a per-leaf `initInFlight` Set guard (try/finally), mirroring the `handleUpdateInFlight` pattern — any method that checks-then-awaits-then-writes shared state needs an in-flight flag.

### 2026-10-17 — lazy-plugins disable→enable lifecycle: onunload deleted the debug flag, stale `item.view` froze positions

- **Problem**: The user's vault runs `lazy-plugins`, which at every app start does `disablePluginAndSave(id)` + `enablePlugin(id)` — an immediate unload→reload cycle (and may also run `hot-reload`). Two verified failures: (1) `onunload` called `clearStickyDiagnostics()`, deleting `document.body.dataset.stickyHeadingsDebug` — so after the disable→enable cycle the re-enabled instance's traces were all silently gated off (tracer blinded exactly when you need it most, during lifecycle debugging). (2) After a re-enable or a view swap while the plugin was dead, `item.view` pointed at the dead view: components kept rendering (font changes applied via rootStyles) but `computeEffectiveTop` read zero rects from the dead `view.contentEl`, returned null (the Oct-15 degenerate-rect skip), and the position froze forever — the "slider dead but font-size recalculates" signature.
- **Solution**: (1) Deleted `clearStickyDiagnostics` and all three call sites — the flag is set by the marker file and harmless to leave set; never clear it. (2) Added `rebindItemViewIfStale(id, item)`: `leaf` objects are stable across view swaps, so `item.view.leaf.view` always names the live view; if it differs from `item.view` (and is a `MarkdownView` with a file), rebind `item.view` + `item.container` and return true. Wired into three places: top of the `onSettingChanged` forEach (follow-up fire-and-forget `handleComponentUpdate` after `updateSettings`), the 5s `healthCheckActiveLeaf` (rebind + full update, then return so the watchdog doesn't double-fire on the stale ref), and at the top of `handleComponentUpdate` itself (rebind at entry, then continue the whole function against the item's fresh view — `({ view } = item)` — so scroller lookups, mount-target drift checks and scroll-capture attach all measure live DOM). (3) Wrapped the entire `onunload` body in one outer try/catch: lazy-plugins awaits `disablePluginAndSave`, so any exception escaping unload breaks the disable→enable cycle and leaves the plugin half-unloaded — nothing may propagate.
- **Files**: `src/plugin.ts`, `src/utils/anchorDebug.ts` (TRACE_BUILD → `trace6-compat`)
- **Key insight**: Plugin lifecycle plugins (lazy-plugins, hot-reload) turn every app start into an unload→reload test. Unload must be exception-proof and must not clean up global state it didn't create (the debug flag); anything cached per-leaf (`item.view`) can go stale across a reload and needs revalidation against the always-live `leaf.view` before use.

### 2026-10-17 — THE SAGA RETROSPECTIVE: why "slider does nothing" took five rounds, ~15 commits, and a file tracer to solve

- **Problem**: One symptom — "the desktop header position slider does nothing" — survived five investigation rounds (Oct 2, Oct 14–17). Each round found and fixed a real, review-verified bug. None was sufficient. The user (correctly) kept reporting the same symptom.
- **Why we were stuck — the failure was a stack of independent layers, and each layer hid the next**:
  1. **Real but insufficient bugs** (found across rounds): degenerate-rect position clobbering on hidden leaves; CSS-class positioning context vs. measured-ancestor mismatch; clamp-saturated formula that killed the slider mathematically; no mount into already-open notes at load; stale `item.view` freezing positions after reload cycles. Each fix passed tests and code review — and changed nothing the user could see, because other layers still failed.
  2. **A hostile test environment**: the vault runs `lazy-plugins` (disable→re-enable at every app start) and `hot-reload`. Every "did the fix work?" test ran against a plugin that was killed, reloaded, or bound to dead views. Stale settings panes absorbed slider drags into dead instances (data.json updated, nothing on screen). Verification results were noise.
  3. **Self-sabotaging diagnostics**: our own `onunload` deleted the debug flag (blinding the tracer exactly during lifecycle events), the trace truncated itself on every load (destroying evidence), and a serial write chain could black-hole all later trace lines. We were debugging with instruments that died with the patient.
  4. **Theory before measurement**: rounds 1–4 shipped fixes for *plausible* root causes. Only after the file-based tracer (write to `debug-trace.jsonl` via the vault adapter, triggered by a `debug.txt` marker) did every finding become measured: `settings-changed → apply-settings → component-update-settings → anchor` lines turned "I think the value doesn't propagate" into "the value propagates and is correct; the DOM write is dead."
  5. **The final bug was invisible to every normal channel**: Svelte's reactive style rewrite silently dead (poisoned scheduler). No console error. Computed values correct (provable in the trace). Element attribute frozen at creation. Only two artifacts could see it: a live DOM inspection (`inlineTop: 0px` from a console paste) crossed with the trace (`effectiveTop` following the slider live). 
- **What was decisive, in order**: (a) the file tracer that survives plugin death; (b) the user's observation that font-size changes "recalculate" the position — the remount signature; (c) one console paste showing `inlineTop: 0px` while the trace showed 69; (d) reading the compiled bundle to confirm the reactive chain was wired correctly — which forced the conclusion that the pipeline itself was dead.
- **Key insights**:
  - When behavior contradicts verified code, suspect the **environment** before the code: lifecycle plugins (lazy-plugins, hot-reload), stale UI panes, and instance churn manufacture ghosts. Audit the vault's plugin ecosystem early in any "my plugin ignores input" bug.
  - **Observability beats theory.** Every round without instrumentation produced a plausible fix; every decisive finding came after the tracer existed. Build the persistent, lifecycle-proof tracer BEFORE the third hypothesis.
  - **Diagnostics must outlive the thing they diagnose.** Never clear debug state in `onunload`; never truncate logs on load; never serialize log writes behind a single operation that can hang.
  - **The user's observations are data.** "Font size recalculates the position" was the exact signature of dead in-place updates + remount-only updates. It took four rounds to treat that sentence as the primary clue.
  - **N independent failures stack.** A fix can be individually correct, tested, reviewed — and change nothing. Absence of visible progress is not evidence the fix was wrong; it may be evidence there are more layers.
  - **UI-critical properties deserve a last-inch imperative write.** The gap between "computed correctly" and "rendered" is where frameworks fail silently.

### 2026-10-17 — Slider dead but font-size refresh recalculates position: poisoned Svelte scheduler, fixed with an imperative style write

- **Problem**: The multi-week saga's final signature: the desktop header position slider did nothing on the user's machine, yet changing font size immediately recalculated the position. Live DOM evidence settled it: while dragging, the trace showed `effectiveTop` computing 57→31→54→72→74→37→69 (every trigger firing, every value correct), but the element's inline `style` attribute NEVER rewrote after creation — it stayed at whatever it was at mount (`top:0px` in the observed session). Font-size changes "worked" only when they coincided with `{#if}` remounts (headings empty→non-empty), where the element is recreated with fresh `rootStyles` — block recreation still worked; in-place reactive updates did not.
- **Root cause**: Svelte 3's scheduler can be permanently poisoned: if any update throws during a shared flush, the flush-scheduled flag is left set and `schedule_flush` never runs again — every subsequent reactive statement is queued but never flushed. All in-place reactive updates (including the `style={rootStyles}` attribute rewrite) die silently, with no console error. This also explains why earlier fixes (correct `effectiveTop` math, anchoring, catch-up init, stale-view rebinds) never fixed the slider: the value was always computed correctly; only the DOM write was dead.
- **Solution**: In `recomputeTop`, after assigning `effectiveTop`, write the position directly: `main.style.top = \`${nextTop}px\``. The `effectiveTop` assignment stays so `rootStyles` remains consistent for remounts and the shadow element. Live traces prove `recomputeTop` runs on every trigger with correct values, so this one line guarantees the DOM agrees with the computation regardless of the reactive pipeline's health. Nothing else changed.
- **Files**: `src/ui/StickyHeader.svelte`
- **Key insight**: When a value is provably computed correctly but the DOM disagrees, write the DOM directly — never let a UI-critical property depend solely on a framework's re-diff pipeline.

### 2026-10-18 — Perf Plans A+B: heading-signature resolve gate + background-leaf gating (zero functional change, workload reduction only)

- **Problem**: `handleResolve` ran on every metadata `resolve` event and unconditionally invalidated the markdown title cache, re-parsed every shown heading (`retrieveHeadings`), rebuilt `getExpectedHeadings` and re-rendered — for EVERY open leaf, including background ones. Findings from audit: the cache was invalidated per resolve → ~0% hit rate; there was no heading-equality gate anywhere. Separately, every `layout-change` event ran a full async update per leaf with no coalescing.
- **Solution**: (1) `computeHeadingSignature` (`level|text|position.start.offset` per heading, newline-joined; missing/empty cache → `''`) stored as `FileResolveEntry.lastHeadingSignature` and written only by paths that commit shown headings (init map.set, same-leaf rebind, `handleComponentUpdate`'s commit branch, post-retrieve in `handleResolve`) so the gate only ever describes shown state; `handleResolve` computes the signature BEFORE `invalidateMarkdownCacheForFile`, stores it only after a parsed (non-timeout) commit, and on a match skips invalidation + retrieveHeadings + updateHeadings entirely (traces `resolve-skip` vs `resolve-rebuild`; TRACE_BUILD → `trace8-ab-gate`). (2) Background-leaf gating: non-active leaves only get `item.dirty = true` (`leaf-dirty-defer`); the `active-leaf-change` 100 ms timer flushes it (`leaf-dirty-flush`). (3) Per-leaf `layout-change` handler debounced 300 ms `{leading, trailing}` — debounce the handler work, not the registration; one fn per init, `.cancel()` on all three teardowns. (4) retrieveHeadings race hygiene: the 1.5 s timeout timer is cleared when render wins; when timeout wins, the losing renderPromise keeps running (its `setCachedTitle` writes still land) with a catch-defuse so nothing surfaces as unhandled. (5) `onSettingChanged` clears all signatures (max/mode change the shown set → one forced recompute). (6) Dead code removed: unregistered `handleEditorChange`, all 5 `dataset.stickyScrollCapture` writes/deletes; same-leaf teardown now returns early (old component stays mounted) if `removeStickyHeader` throws instead of continuing into reinit. (7) Health-check interval `Platform.isMobile ? 30000 : 5000`. (8) Deep-review hardening: the `dirty` flush is mutex-aware (it re-marks + schedules one guarded 300 ms retry via `FileResolveEntry.dirtyFlushRetryTimer` instead of silently dropping the update while `handleUpdateInFlight` holds), and `retrieveHeadings` now returns `{ headings, timedOut }` so a timeout-fallback commit leaves the old signature untouched → the next resolve gate-misses and self-heals via re-parse.
- **Preserved guarantees**: scroll cadence untouched (50 ms lodash throttle on capture scroll), imperative `style.top` write, keyed `{#each (heading.index)}`, remount drift detection, 300/1000 ms settle timers, `handleUpdateInFlight` mutex, `setHeadingsInView` — all untouched; `src/ui/StickyHeader.svelte` not modified. Rendered output identical.
- **Files**: `src/plugin.ts`, `src/types.d.ts`, `src/utils/headingSignature.ts`, `src/utils/anchorDebug.ts` (TRACE_BUILD → `trace8-ab-gate`)
- **Key insight**: An equality gate is only as good as its weakest writer — every path that commits the guarded state must refresh the signature, or the first layout-driven recompute poisons the gate into silently skipping real changes. And compute the signature BEFORE invalidating the cache it protects.
- **Deploy**: `bash sendToNovelVault.sh` runs after commit per conventions. No version bump in manifest.json/package.json (no established per-change bump convention in learning-log/research).
